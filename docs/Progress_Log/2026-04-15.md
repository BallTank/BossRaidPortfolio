## 기술적 고려
### 무엇을 발견했는가
* `ShowPanel(TitlePanelState.Main)` 경로에서 Main panel 활성화 직후 강제 재정렬이 항상 실행되어 scene 기준 배치값을 유지할 수 없었다.
* `TitleMainPanel` 오브젝트의 Animator가 runtime에서 `RectTransform` curve를 반복 적용해 좌우 드리프트를 유발했다.
* dash UI는 기존 `CombatHUDController`에 dedicated fill API가 없어, `PlayerController`가 dash runtime(`IsDashStateActive`, `DashCooldownRemaining`, `DashCooldown`)을 직접 표현할 연결점이 부족했다.

### 무엇을 수정했는가
* `ApplyMainPanelCenterContract()` 메서드를 삭제했다.
* Main panel 활성화 분기에서 해당 메서드 호출을 제거했다.
* Play Mode에서 `TitleMainPanel` Animator를 비활성화하는 `ApplyMainPanelRuntimeLayoutGuard()`를 추가하고 runtime UI bind 경로에서 호출했다.
* `SceneLoader` gameplay target 상수를 `MultiplayerScenePaths.FullGamePlayScenePath`로 바꿔 solo path가 expected multiplayer gameplay scene을 직접 가리키게 했다.
* `EditorBuildSettings`의 `Assets/Scenes/mutiplayer/GamePlayScene.unity` scene entry를 enabled로 돌려 `LoadingScene -> GamePlayScene` 비동기 로드 실패를 제거했다.
* `CombatHUDController`에 `SetDashReadyNormalized(...)`를 추가하고, inspector bind가 비어도 `Image_Dash_Icon_Active3`를 이름 탐색 fallback으로 resolve하도록 보강했다.
* `PlayerController.UpdateDashHudPresentation()`에서 `fill = 1 - (remaining / duration)` 공식을 기본으로 사용하고, `ready = 1` 규칙으로 고정해 매 프레임 HUD에 반영했다(press 직후에는 cooldown 시작값 때문에 `0`부터 시작한다).

### 왜 그렇게 판단했는가
* 요구사항의 핵심은 "배치한 위치 유지"이므로, 런타임 position writer 제거뿐 아니라 Animator curve write 차단까지 함께 해야 화면 드리프트를 실제로 멈출 수 있다.
* same solo transition bug는 runtime 로더 문제가 아니라 scene registration/target 해석 문제였기 때문에, 로직 분기를 크게 바꾸기보다 scene target을 명시하고 build settings 활성 상태를 맞추는 최소 수정이 가장 안전했다.
* dash UI 요청은 gameplay dash authority 수학을 바꾸는 작업이 아니라 presentation sync 작업이므로, 기존 dash state/cooldown source-of-truth를 유지하고 HUD만 읽도록 분리하는 것이 회귀 리스크가 가장 낮았다.
