## 기술적 고려
### 무엇을 발견했는가
* `PlayerController`는 single-player assumption으로 local `IInputProvider`, local HUD init, single camera bind를 전제로 하고 있었다.
* verify gameplay scene의 `Main Camera`가 legacy `Player/CameraRoot` 아래에 있어, old player disable이 곧 camera disable이었다.
* `GameManager`도 scene start 시점의 single player `Health`를 잡고 유지하는 구조였다.
* client jitter를 다시 만들지 않으려면 `client local simulate + host simulate` dual-writer path를 피해야 했다.
* local player cleanup을 startup scene-load hook 하나에만 의존하면 real gameplay scene transition 때 legacy `Player`가 남을 수 있었다.
* client local owner는 movement authority를 Host에 넘긴 대신 avatar rotation도 server replica를 기다리게 되어, no-jitter는 얻었지만 turn feel이 무거워졌다.

### 무엇을 수정했는가
* `PlayerController`에 `RuntimeSimulationMode`, local presentation gate, look-driven camera root option을 추가했다.
* `LocalInputProvider`는 runtime enable/disable과 cursor owner 관리가 가능하도록 바꿨다.
* `MultiplayerPlayerAvatar`는 role별로 `Full / LookOnly / Disabled`를 나누고, client owner input을 `ServerRpc`로 host에 올리는 경로를 추가했다.
* `ThirdPersonCameraController`는 multiplayer gameplay에서 `MultiplayerLocalPlayerRegistry.LocalPlayer`만 local target으로 사용한다.
* `GameManager.SetPlayerHealth(...)`를 추가해 network-spawned local player health로 runtime rebind할 수 있게 했다.
* `MultiplayerGameplaySceneCoordinator`는 synced gameplay load 뒤 player spawn을 시작하고, old player disable 전에 scene main camera를 분리한다.
* `MultiplayerPlayerPrefabBuilder`는 legacy player subtree를 prefab으로 저장하되 embedded `Main Camera`는 제거하도록 설계했다.
* `MultiplayerGameplaySceneCoordinator`는 이제 `SceneManager.sceneLoaded`와 avatar spawn fallback 둘 다에서 scene prep을 보장하고, host/client spawn slot을 좌우로 분리한다.
* `MultiplayerGameplaySceneCoordinator`는 legacy scene `Player`의 spawn 위치/회전을 캐시한 뒤 runtime hierarchy에서 제거하고, cached snapshot을 기준으로 network player를 배치한다.
* `MultiplayerPlayerAvatar`는 runtime hierarchy name을 `hostPlayer` / `clientPlayer`로 고정하고, local owner `LocalInputProvider` look yaw를 spawned rotation에 다시 맞춘다.
* `PlayerController` `LookOnly` 모드는 movement authority는 그대로 Host에 두면서 local visual child에만 presentation rotation을 적용한다.

### 왜 그렇게 판단했는가
* `4.1`은 단순 owner-local shortcut보다 `4.4` host authority input 정리와 이어질 수 있는 base가 더 중요했다.
* client owner를 `LookOnly` local presentation으로 두면 local camera는 유지하면서 movement authority는 host 하나로 고정할 수 있다.
* local camera/HUD는 replicated object가 아니라 local-only binding이어야 하므로 registry 기반 rebinding이 가장 안전했다.
* prefab build는 끝났지만, `4.1`의 runtime smoke는 아직 없으므로 상위 `4. 2인 gameplay scene spawn 동기화`는 계속 열어 둔다.
* 이번 follow-up도 같은 원칙을 유지했다. legacy player cleanup, role visibility, client turn feel만 보강하고 position authority는 Host에 남겨 jitter regression을 피한다.
