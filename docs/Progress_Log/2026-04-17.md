* `Assets/Scenes/mutiplayer/GamePlayScene.unity`의 Terrain block을 점검해, Terrain material(`URP TerrainLit`) 자체보다 `Assets/New Terrain.asset`의 외부 TerrainLayer 참조 누락이 체커 패턴의 직접 원인임을 확인했다.

* bridge layer는 기존 `Assets/Material/NewLayer*.terrainlayer` 내용을 재사용해 runtime에서 `GUID -> TerrainLayer` resolve가 다시 가능하도록 맞췄다.
* python 검증 스크립트로 `Assets/New Terrain.asset` external GUID 7개가 모두 로컬 `.meta`에서 검색되는 상태(`missing_count = 0`)를 확인했다.
* `Progress_Log/README`, `System_Blueprint`, `Technical_Glossary`를 이번 작업 기준으로 동기화했다.

## 맥락노트
* 사용자 증상은 "Terrain에 체스판 패턴이 보이고 Ground 머티리얼이 가려진다"였다.

* Unity batch `-executeMethod`로 TerrainData를 직접 relink하려고 했지만, 현 브랜치의 기존 compile blocker(Beautify asmref + test assembly) 때문에 스크립트 컴파일 단계에서 실행이 중단됐다.
* 그래서 binary TerrainData를 건드리지 않고, TerrainData가 이미 요구하는 GUID를 충족시키는 bridge TerrainLayer를 제공하는 방식으로 복구 경로를 전환했다.

## 기술적 고려
### 무엇을 발견했는가
* Terrain checker 패턴은 `GamePlayScene`의 material slot 문제보다 `New Terrain.asset` 내부 TerrainLayer external GUID 미해결 상태에서 발생했다.
* TerrainData가 이미 7개 layer slot(`fileID 1~7`)을 갖고 있어, 해당 GUID만 복구하면 scene yaml 수정 없이도 resolve 가능했다.

### 무엇을 수정했는가
* `Assets/RecoveredArt/TerrainLayers/LegacyTerrainLayer_01~07.terrainlayer`와 각 `.meta`를 추가했다.
* 각 `.meta` GUID를 TerrainData external GUID와 1:1로 맞췄고, `mainObjectFileID`는 TerrainLayer 기본값(`8574412962073106934`)으로 고정했다.

### 왜 그렇게 판단했는가
* execute-method 방식은 이상적이지만, 현재 브랜치의 기존 컴파일 에러가 해결되지 않으면 자동 relink를 실행할 수 없다.
* GUID bridge 방식은 existing TerrainData/Scene contract를 유지하면서 체커 fallback 원인(미해결 GUID)만 직접 제거하는 최소 변경 경로다.
* 이 방식은 이후 artist 환경과 GUID contract를 맞추기 쉽고, 필요 시 원본 레이어를 찾았을 때도 같은 GUID로 교체만 하면 된다.
