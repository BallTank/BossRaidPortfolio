## 기술적 고려
### 무엇을 발견했는가
* shared locomotion simulation과 multiplayer local presentation은 solo controller 본문에서 분리해도 되는 성격이었다.
* `MultiplayerPlayerAvatar`와 `ThirdPersonCameraController`는 이미 `PlayerController` public API를 기준으로 붙어 있었기 때문에, wrapper를 유지하면 external call site churn을 크게 줄일 수 있었다.
* `LookOnly`는 이미 deprecated 방향이었지만 runtime enum, driver, prefab serialization에 실제 코드 경로로 남아 있었다.

### 무엇을 수정했는가
* `Assets/Scripts/Player/PlayerLocomotionCore.cs`
  * capture / apply / simulate 책임을 옮겼다.
* `Assets/Scripts/Multiplayer/Gameplay/MultiplayerPlayerPresentationDriver.cs`
  * predicted render smoothing
  * predicted render trace
  * presentation runtime state
  * `LookOnly` legacy path 제거 후 `PredictedLocomotion` 전용 driver로 정리했다.
* `Assets/Scripts/Player/PlayerController.cs`
  * multiplayer-heavy method block를 제거하고, new core / driver로 delegate하도록 정리했다.
  * existing public API는 유지했다.
  * `RuntimeSimulationMode.LookOnly`와 old masking/debug field를 제거했다.
* `Assets/Scripts/Multiplayer/Gameplay/MultiplayerPlayerAvatar.cs`
  * `LocomotionRuntimePath` switch와 `HostOnlyCharacterController` fallback을 제거했다.
  * client owner는 항상 `PredictionReconciliation` baseline -> prediction/reconcile 흐름을 타도록 단순화했다.
* `Assets/Resources/Multiplayer/MultiplayerPlayerAvatar.prefab`
  * 제거된 runtime path 직렬화 값을 정리했다.

### 왜 그렇게 판단했는가
* solo와 multiplayer가 같은 locomotion truth를 계속 써야 solo/multiplayer drift를 다시 만들지 않는다.
* multiplayer presentation은 gameplay truth가 아니라 local visual correction layer이므로, `PlayerController` 본문 밖으로 빼는 것이 역할상 더 맞다.
* current project에서는 `MultiplayerPlayerAvatar`와 카메라 쪽 coupling을 한 번에 끊기보다, wrapper 유지 후 내부 책임만 먼저 이동하는 쪽이 더 안전하다.
* deprecated path를 enum과 prefab에 계속 남겨두면 현재 chosen architecture가 흐려지고, 정리 작업 때 dead branch가 다시 섞이기 쉽다.
