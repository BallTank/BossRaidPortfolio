## 기술적 고려
### 무엇을 발견했는가
* current multiplayer runtime은 `step 1~3` 시점까지 `separate action-intent path`는 만들었지만, Host-side persistent state / one-shot reaction snapshot / raw hit log는 아직 없었다.
* boss hit result는 이미 `PlayerController.ReceiveBossAttackHit(...)`로 한 곳에 모여 있었고, player attack damage result도 `DamageCaster.OnAttackWindowResolved(...)`에서 한 번 모을 수 있었다.
* generated `Assembly-CSharp.csproj`는 새 gameplay script 추가 직후 stale 상태가 될 수 있었고, project가 이미 열려 있으면 batch refresh가 정상적으로 solution sync를 끝내지 못했다.

### 무엇을 수정했는가
* `Assets/Scripts/Multiplayer/Gameplay/HostPlayerState.cs`
  * Host authoritative player runtime truth를 담는 struct를 추가했다.
  * HP, active action, accepted action sequence/start tick, reaction consume sequence, hit/stun/death flag를 저장한다.
* `Assets/Scripts/Multiplayer/Gameplay/HostToClientPlayerReactionSnapshot.cs`
  * `hit / stun / death / interrupted action`를 담는 one-shot reaction snapshot struct를 추가했다.
  * `reaction sequence`, `server tick`, `damage`, `result HP`, `source hit type`를 함께 담는다.
* `Assets/Scripts/Multiplayer/Gameplay/HostPlayerReactionResolver.cs`
  * runtime state sync, boss-hit reaction snapshot 생성, attack damage raw hit log 기록을 담당하는 resolver를 추가했다.
* `Assets/Scripts/Multiplayer/Gameplay/MultiplayerPlayerAvatar.cs`
  * server-side host authority contract seed, accepted action state write, boss-hit snapshot 생성, raw hit log 생성 hook를 추가했다.
* `Assets/Scripts/Player/PlayerController.cs`
  * Host resolver가 기존 combat 결과를 받을 수 있도록 `AttackDamageResolved`, `BossAttackResolved` event bridge를 추가했다.

### 왜 그렇게 판단했는가
* `step 4~6`의 목표는 replication 이전에 Host truth layer를 먼저 고정하는 것이다.
* 기존 combat runtime을 전부 다시 짜기보다, 이미 authoritative result가 모이는 지점에 event bridge를 두는 편이 범위가 작고 회귀 위험이 낮다.
* `HostPlayerState`와 `HostToClientPlayerReactionSnapshot`을 먼저 만들면 다음 단계인 `Replicator / Applier / display-only remote` 설계가 더 단순해진다.
* `raw hit log`는 later boss aggro rule이 의존할 데이터이므로, full replication 전에라도 Host에서 누가 언제 얼마를 넣었는지 기록 경로를 먼저 확보하는 편이 맞다.
