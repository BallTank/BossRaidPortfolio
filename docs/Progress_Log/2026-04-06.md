## 기술적 고려
### 무엇을 발견했는가
* current boss mirror snapshot은 `MultiplayerPlayerAvatar` 안에서 animator state와 hash 중심으로 캡처되고 있어, dedicated boss authority contract라고 부르기에는 player-avatar path에 너무 의존적이었다.
* boss runtime에는 `current attack id`와 `attack start tick/time`을 stable하게 보관하는 dedicated bookkeeping이 아직 없었다.
* dedicated network actor prefab을 새로 추가하지 않아도, `MultiplayerRuntimeRoot` 위의 bridge + NGO named message 조합으로 boss send/apply responsibility를 `MultiplayerPlayerAvatar`에서 분리할 수 있었다.
* semantic-only apply를 선택했기 때문에 `Move / Search / Basic / Lunge / Dead`는 작은 state contract로 충분하지만, phase intro / AoE는 best-effort visual rule을 허용하는 쪽이 current scope에 맞았다.
* direct snap apply는 packet timing에 따라 client boss turn/stop이 거칠게 보일 수 있어 `step 3` smoothing을 시도했지만, current verify에서는 오히려 jitter regression이 먼저 드러났다.
* rollback 뒤에도 client boss가 root는 이동하지만 walk blend가 0으로 눌리는 경우가 있어, same snapshot multi-apply와 weak delta speed가 follow-up suspect로 드러났다.
* attack 3/4는 boss attack state와 animation contract 자체는 이미 맞았고, 빠진 것은 spawned projectile/AoE visual의 remote replay뿐이었다.

### 무엇을 수정했는가
* multiplayer gameplay layer에 `BossAuthoritativeState` struct와 관련 enum을 추가했다.
* `BossController`에 `CaptureAuthoritativeState(...)`, locomotion/phase resolve helper, active attack bookkeeping helper를 추가했다.
* `BossAttackState.Enter()/Exit()`와 death path에 bookkeeping 연결을 넣어 attack 시작과 종료 기준이 boss gameplay runtime에서 직접 기록되게 했다.
* `MultiplayerBossAuthorityBridge`를 추가해 Host가 boss snapshot을 capture/send 하고, client가 local disabled boss에 transform + semantic animator state를 display-only로 apply하게 했다.
* `MultiplayerRuntimeRoot`가 bridge component를 자동으로 보유하게 했고, `MultiplayerPlayerAvatar` 안의 old boss mirror RPC/capture/apply 코드를 제거했다.
* same-day cleanup으로 `MultiplayerPlayerAvatar`의 high-volume action trace, runtime role configuration log, disconnect profile debug path, `MultiplayerSessionService`의 `MultiplayerConnectionDebug` path, boss lunge root-motion debug log plumbing을 제거했다.
* same-day rollback으로 `MultiplayerBossAuthorityBridge`는 다시 latest authoritative state direct apply + packet delta speed 계산 기준으로 돌아왔다.
* same-day follow-up으로 `MultiplayerBossAuthorityBridge`는 latest received boss tick을 한 번만 consume하고, move/search state에서는 delta speed가 약해도 stable display speed를 유지하게 했다.
* `BossReplicatedEffectEvent` DTO와 `boss-replicated-effect` named message를 추가했다. Host는 `ProjectileAttackPattern`/`AoEAttackPattern`에서 실제 spawn 순간 effect event를 큐에 적재하고, `MultiplayerBossAuthorityBridge`는 이를 reliable sequenced로 보내며, client는 `BossProjectile.InitializeDisplayOnly(...)`, `BossProjectile.InitializeImpactMarker(...)`, `AoEAttackPattern.PlayReplicatedDisplayAoE(...)`를 통해 attack 3 projectile과 attack 4 red circle/falling fire를 display-only로 재생한다.

### 왜 그렇게 판단했는가
* current step의 핵심은 client apply가 아니라 `Host truth shape`를 먼저 고정하는 것이므로, packet shape를 작고 explicit하게 두는 편이 맞았다.
* attack start tick은 multiplayer bridge가 아직 없더라도 later authority send가 바로 쓸 수 있게 stable source가 필요했다.
* step 2에서는 separate boss prefab/network object보다 runtime-root bridge가 구현 비용과 lifecycle risk가 더 작았고, still dedicated code path라는 목적을 만족했다.
* client local boss logic를 계속 disabled로 유지해야 authority가 다시 섞이지 않으므로, bridge는 gameplay logic를 건드리지 않고 display-only apply만 수행하게 두는 편이 가장 안전했다.
* `step 3` smoothing이 current verify에서 regression을 만든 이상, stable Step 2 baseline으로 먼저 되돌리고 later separate task로 다시 다루는 편이 더 안전하다고 판단했다.
* direct-apply baseline에서도 same snapshot을 `callback + Update` 양쪽에서 반복 적용하면 locomotion delta가 0으로 눌릴 수 있으므로, consume gate를 먼저 세우고 move/search speed에 host-speed floor를 두는 편이 가장 작은 수정으로 walk blend regression을 줄인다고 판단했다.
* movement/basic/lunge/death가 실제 runtime test에서 이미 통과한 뒤에는 per-action trace, disconnect/session continuity debug, lunge debug spam이 새 문제 탐지보다 console noise를 더 크게 만들었기 때문에, now-useful 경고/오류 로그 위주로 남기는 쪽이 유지보수에 더 낫다고 판단했다.
* attack 3/4 문제는 Host gameplay truth 자체가 아니라 remote client visual replay 누락이었으므로, `BossAuthoritativeState`를 더 키우기보다 separate effect event path를 추가하는 편이 영향 범위가 작고 기존 step 1-2 contract와도 충돌하지 않았다.
